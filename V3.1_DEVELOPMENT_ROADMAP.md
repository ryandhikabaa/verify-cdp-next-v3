# Verify CDP Web V3.1 — Development Roadmap

**Status:** ACTIVE — successor to the frozen V3 digital contract. Phases 0+ are open; no V3.1 code has been implemented yet.  
**Baseline:** `verify-cdp-next-v3` as frozen in `V3_DEVELOPMENT_ROADMAP.md` (payload, matrix, renderer geometry, QR-anchored decoder).  
**Target project:** `verify-cdp-next-v3`  
**Last updated:** 2026-09-03 (contract revision 2)

## 1. Purpose

V3.1 is a controlled follow-on to web V3. It does **not** reopen the V3 payload, matrix, or printed-layout geometry. It changes two product contracts that V3 left local and implicit:

1. **QR source.** QR generation is **not** this project's job. Another service already owns custom QR. This generator only `POST`s `{ hvalue }` to `https://authenticity-qr.pstlocal.net/api/Checking/qrcode-generate-dynamic` and places `imgOutput` into the existing QR rectangle. Canvas size, quiet zone, gap, pattern size, and composite layout stay exactly as V3.
2. **Persistence.** V3 still writes into `dotvera_v2.pattern_generated_v21` through runtime `CREATE/ALTER`. V3.1 moves to a dedicated `dotvera_v3` database, owned by Prisma migrations. The new database is **clean except `user`**: empty `pattern_generated` and `pattern_detection`, copied user rows only.

V2 and the frozen V3 digital codec remain compatibility baselines. Existing v2/v3 printed samples are not migrated into `dotvera_v3` and must not be invalidated by this work.

## 2. Target Layout

Unchanged from V3:

```text
[ QR ] [ fixed gap ] [ one rectangular pattern ]
```

The pattern stays on the **right side of the QR**.

### Layout principles (frozen, do not reopen)

- QR is the geometric anchor.
- Only one rectangular pattern is decoded.
- The pattern crop is deterministic from the QR geometry.
- Pattern identity is `pattern_payload`. QR content is **not** unique pattern identity.
- No left/right candidate search in the primary V3 path.
- Layout version remains `v3-qr-pattern`.
- QR visual size, pattern visual size, one-module gap, right margin, and footer remain the V3 renderer contract.

### What V3.1 is allowed to change inside that layout

- The **source of QR pixels** inside the locked QR rectangle.
- The **stored metadata** for that QR (`qr_payload`, `qr_hvalue`, `qr_secret1`, `qr_secret2`, `qr_image`).
- The **database** that records generated and detected rows.

The renderer must still place a QR canvas of the current V3 size, then a one-module gap, then the V3 pattern. The API image is scaled into the existing QR rectangle. The API image's intrinsic pixel size, QR version, and module count must **not** drive layout.

## 3. Scope Boundaries

### In scope

- Generator input for QR hidden value (`hvalue`): `A-Z a-z 0-9`, length 1–7.
- Server-side pass-through to the locked QR host (this project does not generate QR).
- HTTP 200 gate: any non-200 response aborts generation and shows an error popup.
- Replace local QR pixels with `data[].imgOutput` without changing layout measurements.
- Prisma setup, `dotvera_v3` database, and versioned migrations.
- New empty `pattern_generated` and `pattern_detection` tables; copy **only** `user` rows.
- Store QR payload, hvalue, secret1, secret2, and image on generated rows; store the same QR metadata on detection rows so mobile online verify can persist them.
- Pattern save/list/delete/batch/verify APIs switched onto the new schema.
- Operator catalog: QR secrets visible on the **detail** view only.
- Remove unused `/api/patterns/next-index` (legacy serial counter; unrelated to `imgOutput`).
- Focused tests for hvalue validation, QR API failure, geometry lock, and Prisma schema.

### Out of scope until explicitly approved

- Changes to the V3 payload codec, 64×32 matrix, Reed–Solomon/CRC, or crop geometry.
- Changing QR/pattern/gap/footer pixel sizes to match the API image.
- Deriving `qrModuleCount` from the new QR payload (that would change the gap).
- Writing V3.1 rows into `dotvera` or `dotvera_v2`.
- Migrating historical `pattern_generated_v21` or `pattern_detection` rows. `dotvera_v3` starts empty except `user`.
- Generating QR inside this repo (no `qrcode` library as pixel source; no second QR service).
- Calling the QR host from the browser (CORS and secret leakage). The Next.js route is a pass-through to the locked URL, not a generator.
- Hitting the QR API on every live-preview keystroke.
- Implementing the mobile scanner in this roadmap. Web verify/detection APIs must still accept the QR metadata mobile will POST later.
- Reopening V1/V2 compatibility in the primary verifier.
- Physical reprint of V3 samples that still use the local locked QR.

### Carried from V3 (not blockers for Phase 0–5)

- Formal browser/device matrix (desktop webcam, Android Chrome, iPhone Safari).
- Physical print pilot (7 mm down to 1.1 mm).
- HTTPS/local deployment and camera-permission fallback documentation.

## 4. Development Rules

1. Read the current V3 implementation and this document before editing.
2. Keep V3 payload/matrix/renderer geometry tests green; V3.1 tests add coverage, they do not replace it.
3. Define or update a contract before implementing dependent code.
4. Replace **only** QR pixels. Assert layout metadata equality against the current V3 renderer.
5. Validate `hvalue` on both client and server: required, trimmed, alphabet `A-Z a-z 0-9`, length 1–7. Do not silently truncate.
6. The generator must not continue after a non-200 QR API response. Show a popup and leave the previous successful composite untouched.
7. Do not generate QR in this project. The Next.js route only forwards `{ hvalue }` to `https://authenticity-qr.pstlocal.net/api/Checking/qrcode-generate-dynamic`. The browser never calls that host directly.
8. Prisma owns `dotvera_v3`. Do not add runtime `CREATE TABLE` / `ALTER TABLE IF NOT EXISTS` for V3.1 tables.
9. `pattern_payload` is the unique generated identity (replaces `serial` / `pattern_seed` / split payload columns). Verify lookup uses `pattern_payload`.
10. Do not treat scanned QR text as pattern identity. Store scanned text as `qr_value`. Store API QR metadata (`qr_payload`, `qr_hvalue`, `qr_secret1`, `qr_secret2`) on both generated and detection rows.
11. Copy **only** user rows, with existing ids and password hashes. Do not re-hash. Do not copy patterns or detections.
12. Record decisions, test results, and known limitations in this document.

## 5. Frozen V3 Contracts V3.1 Must Preserve

These are closed. V3.1 may only change them through a new documented decision.

| Contract | Locked value |
|---|---|
| Layout version | `v3-qr-pattern` |
| Arrangement | QR left, one rectangular pattern right |
| QR visual size | Same as current V3 generator (`gridSize * dotSize` canvas) |
| QR module model used for gap | Current V3 locked QR: version-2, 25 modules, 1-module quiet zone |
| Gap | One QR module, derived from that locked module size |
| Pattern matrix | 64 rows × 32 columns |
| Pattern visual height | Equal to QR symbol height excluding quiet zone |
| Payload | 1–24 characters `A-Z a-z 0-9 - _`, CRC-16 + RS(32,22) |
| Verifier | QR-anchored, current-frame, V3-only |
| Identity | Pattern payload, not QR content |

Implementation today that V3.1 must not silently keep:

- `QRCode.create` / `QRCode.toCanvas` as the source of QR **pixels**.
- Hard-coded `LOCKED_QR_PAYLOAD = 'https://puragroup.com'` as stored `payload_qr`.
- Writes to `pattern_generated_v21` in `dotvera_v2`.
- Runtime schema mutation in `lib/db/dotvera.ts` for the V3.1 database.

`QRCode.create` may remain **only** if a later decision proves it is required to reproduce the locked 25-module geometry. It must not paint the QR that the user sees or downloads.

## 6. New Contracts

### 6.1 QR generate API

QR generation lives in **another project**. This repo must not implement a QR encoder as the product QR. It only requests an image from the existing service and places that image next to the V3 pattern, same as today except the QR pixels come from `imgOutput`.

**Locked upstream URL (not optional, not a second generator)**

```text
POST https://authenticity-qr.pstlocal.net/api/Checking/qrcode-generate-dynamic
Content-Type: application/json

{ "hvalue": "TELKOM" }
```

Env `QR_GENERATE_API_URL` may repeat that exact URL for deployment wiring. It must not point at a different generator. Changing the host is a contract change, not a config tweak.

**App-facing pass-through (required)**

```text
POST /api/qr/generate
Content-Type: application/json

{ "hvalue": "TELKOM" }
```

The browser talks only to this route. The route forwards the JSON body to the locked URL, applies the HTTP 200 gate, and returns the mapped fields. It does not create QR pixels itself.

**`hvalue` validation (client and pass-through)**

- Required.
- Trimmed.
- Alphabet locked: `A-Z`, `a-z`, `0-9`.
- Length 1–7 inclusive.
- Case-sensitive as submitted after trim (`Telkom` ≠ `TELKOM`).
- Reject empty, whitespace-only, other characters, and length > 7 **before** any upstream call.
- Do not silently truncate; show a validation popup.
- Dedicated generator input. Do not reuse the V3 pattern payload field.

**Success gate**

Generation, preview-with-QR, save, download, and batch may continue only when **all** of the following are true:

1. Upstream HTTP status is exactly `200`.
2. JSON body parses.
3. `status` is `"success"` (if present).
4. `data` is a non-empty array.
5. `data[0].imgOutput` is a non-empty string.

Any other HTTP status (`4xx`, `5xx`, `0`/network, timeout) **stops the flow**. Do not render, save, or download a composite. Show an error popup. Do not retry automatically.

A `200` response with missing `imgOutput` is also a hard stop (treat as contract failure, not as HTTP success).

**Expected success body**

```json
{
  "status": "success",
  "message": "QR Code successfully generated",
  "data": [
    {
      "secret1": "A8C2D3E0AECE",
      "secret2": "1CE6",
      "qrcode": "b0df621A",
      "hvalue": "TELKOM",
      "imgOutput": "base64image"
    }
  ]
}
```

**Field mapping**

| API field | Stored column | Meaning |
|---|---|---|
| `data[0].qrcode` | `qr_payload` | Content encoded in the custom QR |
| `data[0].hvalue` | `qr_hvalue` | Operator-supplied hidden value |
| `data[0].secret1` | `qr_secret1` | API secret 1 |
| `data[0].secret2` | `qr_secret2` | API secret 2 |
| `data[0].imgOutput` | `qr_image` | Base64 (or data-URL) QR image used as pixels |

`imgOutput` is the only visual QR. It is drawn into the current V3 QR rectangle and composited with the pattern exactly as the local QR is today. Layout, gap, and pattern size do not change.

`imgOutput` may arrive as raw base64 or as a `data:image/...;base64,` URL. Normalize to a data URL before drawing and storing. Do not assume PNG vs JPEG; accept either as long as the browser can decode it.

**Geometry rule for `imgOutput`**

```text
create QR canvas at the current V3 QR pixel size
→ decode imgOutput
→ draw it into that canvas (contain, no layout growth)
→ pass that canvas to renderV3QrPatternToCanvas
```

Do **not**:

- Resize the composite to the API image size.
- Recompute module count from `qrcode`.
- Change gap, pattern height, right margin, or footer because the API image is a different resolution.

**When the API is called**

| Action | Call QR API? |
|---|---|
| Typing pattern payload (live preview debounce) | No. Reuse last successful QR image, or show the pattern beside an empty locked-size QR slot. |
| Typing `hvalue` | No. Invalidate the cached QR. |
| Update preview | Yes, if there is no valid cached QR for the current `hvalue`. |
| Download / Simpan / Generate batch | Yes for every composite that does not already have a successful QR for that item. |
| Batch item N | Yes, one call per item. Same `hvalue`, unique API `qrcode`/secrets/image. |

Cache key: current `hvalue` + successful `imgOutput`. Changing `hvalue` discards the cache. Changing only the pattern payload may reuse the cached QR so the operator is not charged an API call per keystroke.

**Batch failure policy**

If any item's QR API call is not HTTP 200 (or fails the body gate), stop the batch. Do not save a partial batch. Show one error popup. Do not leave orphan rows in `pattern_generated`.

**Timeouts**

- Pass-through timeout: 15 seconds, no automatic retry.
- Classify failures: validation, upstream HTTP, timeout, malformed body, image-decode.

**Error popup copy (Indonesian, generator UI)**

- Validation: `Hidden value maksimal 7 karakter.` / `Hidden value wajib diisi.`
- Non-200: `Gagal generate QR (HTTP {status}). Proses dihentikan.`
- Network/timeout: `Gagal menghubungi layanan QR. Proses dihentikan.`
- Malformed 200: `Respon QR tidak valid. Proses dihentikan.`

Reuse the existing generator validation dialog. Do not fail silently into `console.error`.

### 6.3 Table `user`

Same columns, types, constraints, and indexes as v1/v2. Copy **data** from the local `dotvera_v2.user` rows (ids, nama, username, password_hash, role, timestamps, last_login). Do not generate new admin passwords during the copy.

```text
user
  id             UUID PK DEFAULT gen_random_uuid()
  nama           VARCHAR(255) NOT NULL
  username       VARCHAR(100) NOT NULL UNIQUE
  password_hash  TEXT NOT NULL
  role           VARCHAR(50) NOT NULL
  create_at      TIMESTAMPTZ NOT NULL DEFAULT now()
```

Index: `idx_user_username` on `username`.  
Trigger: `set_user_update_at` (same behaviour as v2).

Prisma model maps to `@@map("user")` because `user` is reserved. Column names in PostgreSQL stay snake_case / exact v2 names, including `password_hash` and `create_at`.

Position columns are removed: `left_position`, `qr_position`, `right_position`, `pattern_position`.

```text
pattern_generated

  qr_secret2         TEXT NOT NULL          -- API data[].secret2
  qr_image           TEXT NOT NULL          -- normalized data URL of imgOutput
  pattern_payload    VARCHAR(24) NOT NULL UNIQUE
  image_data         TEXT                   -- composite canvas export (QR + pattern)
  image_blob         BYTEA                  -- binary of that composite
  density            DOUBLE PRECISION NOT NULL
  size               INTEGER
  style              VARCHAR(100)
  layout_version     VARCHAR(50) NOT NULL DEFAULT 'v3-qr-pattern'
  qr_width_px        INTEGER
  qr_height_px       INTEGER
  pattern_width_px   INTEGER
  pattern_height_px  INTEGER
  gap_px             INTEGER
  canvas_width_px    INTEGER
  canvas_height_px   INTEGER

  update_at          TIMESTAMPTZ NOT NULL DEFAULT now()
```

**Column mapping from local `dotvera_v2`**

Indexes:

- unique `pattern_payload`
- `layout_version`
- `qr_hvalue`

### 6.5 Table `pattern_detection`

Keep the v2 detection audit columns. Align identity/QR fields with `pattern_generated`. **QR secrets stay on detection rows** so the later mobile online flow can POST them and the web verify API can persist them. The table is created empty; no v2 detection rows are copied.

```text
pattern_detection
  id                      UUID PK DEFAULT gen_random_uuid()
  generated_id            UUID NULL REFERENCES pattern_generated(id) ON DELETE SET NULL
  label                   VARCHAR(255) NOT NULL          -- display copy of pattern_payload
  "deviceID"              VARCHAR(255) NOT NULL
  status                  VARCHAR(50) NOT NULL
  notes                   TEXT
  image_data              TEXT                           -- scan evidence, not the generated composite
  latitude                DOUBLE PRECISION
  longitude               DOUBLE PRECISION
  layout_version          VARCHAR(50)
  qr_payload              TEXT                           -- API qrcode / generated.qr_payload
  qr_hvalue               VARCHAR(7)                     -- hidden value
  qr_secret1              TEXT                           -- API secret1; stored for mobile online verify
  qr_secret2              TEXT                           -- API secret2; stored for mobile online verify
  qr_value                TEXT                           -- raw scanned QR text from the camera
  qr_format               VARCHAR(50)
  qr_detected             BOOLEAN NOT NULL DEFAULT FALSE
  qr_bounds               JSONB
  pattern_payload         VARCHAR(24)                    -- canonical identity, aligned with pattern_generated
  pattern_decode_payload  TEXT                           -- raw scanned pattern text
  pattern_crop_bounds     JSONB
  rectangular_score       DOUBLE PRECISION
  pattern_confidence      DOUBLE PRECISION
  payload_mode            VARCHAR(20)
  decrypt_succeeded       BOOLEAN
  checksum_valid          BOOLEAN
  created_at              TIMESTAMPTZ NOT NULL DEFAULT now()
  updated_at              TIMESTAMPTZ NOT NULL DEFAULT now()
```

`qr_image` stays on `pattern_generated` only (the generate-time QR pixels). Detection stores scan evidence in `image_data`, not a second copy of `imgOutput`.

**Alignment rules**

| Generated | Detection | Rule |
|---|---|---|
| `id` | `generated_id` | Set when lookup hits; null on COUNTERFEIT |
| `pattern_payload` | `pattern_payload`, `label` | Verify looks up `pattern_generated.pattern_payload = scanned pattern` |
| `qr_payload` | `qr_payload` | Prefer client-submitted value (mobile online). If omitted, copy from the matched generated row |
| `qr_hvalue` | `qr_hvalue` | Same: client-submitted, else copy from match |
| `qr_secret1` | `qr_secret1` | Persist when the client sends it (mobile online). Else copy from the matched generated row |
| `qr_secret2` | `qr_secret2` | Same as `qr_secret1` |
| — | `qr_value` | Raw camera QR text; not identity |
| `layout_version` | `layout_version` | Persist `v3-qr-pattern` |
| `image_data` (composite) | `image_data` (scan) | Different meaning; keep both tables' columns |

Indexes:

- `"deviceID"`
- `qr_detected`
- `payload_mode`
- `pattern_payload`
- `generated_id`
- `layout_version`

Trigger: `set_pattern_detection_updated_at` (column remains `updated_at`, as in v2).

Verify request body stays compatible with the current web scanner (`pattern_decode_payload`, `qr_value`, `layout_version`, …) and is extended for mobile online:

```text
pattern_decode_payload     required (V3 pattern identity)
qr_value                   optional raw camera QR text
qr_payload                 optional API qrcode
qr_hvalue                  optional hidden value
qr_secret1                 optional API secret1
qr_secret2                 optional API secret2
layout_version             v3-qr-pattern
```

Web V3.1 may omit the secret fields; the server then copies them from the matched `pattern_generated` row. Mobile online is expected to POST the QR metadata it holds and have those values stored on `pattern_detection`.

Verify lookup:

```text
scanned pattern_decode_payload
  → validate V3 payload shape
  → SELECT id, pattern_payload, qr_payload, qr_hvalue, qr_secret1, qr_secret2
      FROM pattern_generated
     WHERE pattern_payload = $1
     LIMIT 1
  → AUTHENTIC if row exists, else COUNTERFEIT
  → INSERT pattern_detection with:
       raw scan fields
       canonical pattern_payload / generated_id / layout_version
       qr_payload, qr_hvalue, qr_secret1, qr_secret2
         (client-submitted if present, else copied from the match)
```

QR scan value (`qr_value`) is recorded, not used as the identity key. Authenticity remains a `pattern_payload` lookup.

### 6.6 Prisma ownership

Prisma is the only schema migrator for `dotvera_v3`.

Deliverables:

- `prisma/schema.prisma`
- `prisma/migrations/` (SQL migrations checked in)
- `prisma/seed.ts` (user copy / admin fallback)
- `lib/db/prisma.ts` (single PrismaClient)
- npm scripts: `prisma:generate`, `prisma:migrate`, `prisma:seed`

Rules:

- Initial migration creates `user`, `pattern_generated`, `pattern_detection`, indexes, and update triggers.
- `ensureDotveraSchema()` must not create V3.1 tables. After cutover it is removed from the V3.1 request path or restricted to a legacy no-op.
- Raw `pg` queries in `app/api/**` are replaced with Prisma (or a thin repository that uses Prisma).
- Never hand-edit generated Prisma client files.
- `image_blob` is `Bytes`. `qr_bounds` / `pattern_crop_bounds` are `Json`.
- `"deviceID"` is mapped with `@map("deviceID")`.

User seed order:

1. Create empty `dotvera_v3`.
2. Run Prisma migrate.
3. Copy all rows from `dotvera_v2.user` (preferred) with original `id` and `password_hash`.
4. If `dotvera_v2` is unreachable, fall back to the existing admin env seed (`DOTVERA_ADMIN_*`) and record that fallback in the change log.

Do **not** copy `pattern_generated`, `pattern_generated_v21`, or `pattern_detection` into `dotvera_v3`. Those tables start empty. The new database is clean except `user`.

### Phase 2 — QR API pass-through and validation

**Goal:** a single, testable way to obtain `imgOutput` from the other project's QR service.

Required behaviour:

- Client and server reject `hvalue` outside `A-Z a-z 0-9` or longer than 7 characters without calling upstream.
- Pass-through POST JSON `{ hvalue }` to `https://authenticity-qr.pstlocal.net/api/Checking/qrcode-generate-dynamic`.
- HTTP 200 + valid `imgOutput` returns `{ qr_payload, qr_hvalue, qr_secret1, qr_secret2, qr_image }`.
- Non-200 returns a structured error with the HTTP status; no partial data.
- Timeout and network errors are explicit.
- The locked URL is the only generator. Env may repeat it; it must not retarget another host without a contract change.
- Secrets never appear in client-side logs in production builds.

**Deliverables:**

- `app/api/qr/generate/route.ts`
- Shared `hvalue` validator.
- Unit tests: too-long, empty, 200 success, 400/500 stop, malformed 200 stop, timeout.
- Fixture of a fake `imgOutput` for renderer tests (do not depend on the live host in CI).

**Gate:** tests pass without the live QR host. A manual live-host check is recorded in the change log when the network is available.

### Phase 3 — Generator QR swap (geometry locked)

**Goal:** the generator still looks and measures like V3, but the QR rectangle shows the API image.

Required behaviour:

- New `hvalue` input in `GeneratorControls` (max 7, dedicated field).
- `renderCompositePattern` draws `qr_image` into the existing QR canvas size, then calls `renderV3QrPatternToCanvas` unchanged.
- Layout metadata (`qrWidthPx`, `qrHeightPx`, `patternWidthPx`, `patternHeightPx`, `gapPx`, `contentWidthPx`, `contentHeightPx`) equals current V3 measurements for the same settings.
- Pattern pixels remain the V3 matrix render. Only the QR rectangle may differ from today's local QR.
- Update preview / download / save / batch all go through the HTTP 200 gate.
- Live payload typing does not call the QR API.
- Error popup on failure; previous preview remains.
- `PreviewModal` uses the same QR source as the workspace (no second local `QRCode.toCanvas` path).

**Deliverables:**

- Generator control + workspace changes.
- Geometry regression: compare layout metadata to the current V3 renderer test vectors.
- Pixel test: pattern region unchanged; QR region allowed to change.
- Loading state while the QR API is in flight.

**Gate:** V3 render tests still pass for pattern/gap/margin. A new test proves a stub API image is drawn at the locked QR size and does not change composite width/height.

### Phase 4 — Persist on the new schema

**Goal:** save/list/delete/batch/image APIs write `pattern_generated` in `dotvera_v3`.

Required behaviour:

- POST one pattern stores every §6.4 column, including QR secrets and `qr_image`.
- POST batch is transactional; QR failure or insert failure rolls back the whole batch.
- GET catalog returns `pattern_payload` as the public id (replacing `serial`).
- DELETE keys off `pattern_payload`.
- Image route returns the composite `image_blob` / `image_data`.
- Request validation no longer requires `pattern_seed === serial` or the locked URL.
- Authenticated catalog **list** hides `qr_secret1` / `qr_secret2`. Authenticated **detail** shows them.
- Delete `/api/patterns/next-index`, its middleware allow-list entry, and its API-docs row. It is unused by the generator and is not part of the `imgOutput` flow.

**Deliverables:**

- Updated `app/api/patterns/**`.
- Delete `app/api/patterns/next-index/route.ts` and its docs/middleware entries.
- Updated `PatternDoc` / helpers (`serial` → `pattern_payload`).
- Stored-patterns panel: list without secrets; detail shows `qr_secret1` / `qr_secret2`.
- API docs (`lib/api-docs.ts`) for the new fields and verify QR metadata.

**Gate:** save one and save batch against `dotvera_v3`, reload catalog, download stored composite. No writes to `dotvera_v2`.

### Phase 5 — Verify and detection alignment

**Goal:** the QR-anchored V3 decoder still submits the same scan evidence; the server looks up `pattern_payload` on the new table and writes aligned detection rows.

Required behaviour:

- Scanner contract unchanged: current-frame crop, `layout_version: v3-qr-pattern`, `pattern_decode_payload`, `checksum_valid`.
- Server lookup uses `pattern_generated.pattern_payload`.
- Detection insert fills canonical columns (`pattern_payload`, `generated_id`, `layout_version`) plus QR metadata (`qr_payload`, `qr_hvalue`, `qr_secret1`, `qr_secret2`) and existing raw columns.
- Accept optional `qr_payload` / `qr_hvalue` / `qr_secret1` / `qr_secret2` on the verify POST so mobile online can persist them. If omitted, copy from the matched generated row.
- AUTHENTIC / COUNTERFEIT rules unchanged (row exists vs not).
- History / dashboard / export read the new table without dropping geo, device, or image evidence.
- Public verify **response** stays AUTHENTIC/COUNTERFEIT plus existing public fields. Do not echo secrets back to unauthenticated clients. Persistence of secrets on `pattern_detection` is required.

**Deliverables:**

- Updated `app/api/verify/route.ts` and history routes.
- Prisma queries only.
- Focused verify tests with a stub generated row.

**Gate:** digital V3 sample whose `pattern_payload` exists in `dotvera_v3` returns AUTHENTIC; unknown payload returns COUNTERFEIT; detection row contains both raw and canonical fields.

### Phase 6 — Test matrix and cutover

**Goal:** prove the new flow without regressing the frozen codec.

#### Unit / contract

- `hvalue` length and alphabet.
- Pass-through 200 / non-200 / malformed body.
- `imgOutput` raw base64 and data-URL normalization.
- Geometry lock (layout metadata equality).
- Pattern-region pixel lock.
- Prisma schema matches §6 (migration SQL review).
- Verify lookup by `pattern_payload`.

#### Existing V3 suites (must stay green)

- Payload, Reed–Solomon, vectors, matrix, render, generator contract, web-decoder.

#### Manual

- Live QR host `hvalue=TELKOM` once, when the network allows.
- Failed host / forced non-200 shows popup and does not save.
- Login with copied v2 user.
- Save, batch abort, catalog, verify authentic/counterfeit.

**Gate:** targeted tests pass; `tsc --noEmit` on touched files is clean. Pre-existing app-shell typing errors are classified, not “fixed” as part of this phase unless they block the build.

### Phase 7 — Carried V3 acceptance (unchanged owners)

Not introduced by V3.1, still required before any physical freeze of custom-QR prints:

1. Digital samples with the custom QR decode on the web verifier (ZXing must still find finder patterns on the API image).
2. Small physical pilot.
3. Desktop / Android Chrome / iPhone Safari.
4. Lighting, distance, angle, reflection.
5. Only then freeze a printed custom-QR batch.

**Residual risk:** a custom QR image may be harder for ZXing than the local `qrcode` library output. If camera detection drops, the fix is image-quality / contrast of `imgOutput` or a documented decoder tweak — **not** a layout-size change — unless a new contract explicitly reopens geometry.

**Gate:** recorded device results. Do not print a production batch until a custom-QR digital scan succeeds.

## 12. Residual Risks

| Risk | Class | Mitigation |
|---|---|---|
| Custom QR image is not ZXing-readable | External-service / image | Scan a live `imgOutput` digitally before any print; do not change crop geometry to compensate |
| QR host down | External-service | Hard stop + popup; no local QR fallback (fallback would violate the custom-QR product rule) |
| CORS if someone calls the host from the browser | Implementation | Pass-through only; no client `fetch` to `pstlocal.net` |
| `qrcode` payload is a short version-1 symbol and would shrink the layout | Contract | Never derive layout from that payload; lock V3 QR canvas size; only swap pixels |
| Batch of 100 sequential QR calls is slow or rate-limited | External-service | Progress UI; abort on first failure; consider a lower batch cap if the host requires it |
| Secrets echoed on public verify responses | Security | Persist secrets on `pattern_detection`; do not return them on unauthenticated verify responses; catalog detail is authenticated |
| Dual-write to `dotvera_v2` during cutover | Compatibility | Single target `dotvera_v3`; v2 remains untouched |
| User copy misses a row or re-hashes passwords | Data | Copy raw `password_hash`; verify login with a known v2 account before dropping access to v2 |
| Accidental copy of old patterns/detections into `dotvera_v3` | Data | Seed copies `user` only; generated and detection tables stay empty |
